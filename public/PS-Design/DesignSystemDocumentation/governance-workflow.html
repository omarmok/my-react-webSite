Design system handover cycle and contribution governance for partners

This chart explains how external companies receive the approved design system, how they use it and propose improvements or additions, and how AMN reviews, approves, merges and publishes them so that all projects benefit.

Governance Principles

Eight core principles that govern every step of the workflow
01Single Source of Truth
There is one official central source for the design system; any copy outside it is not approved.
02Reuse First
Use what exists before creating something new, and submit an improvement request instead of inventing your own alternative.
03Controlled Contributions
Improvements and additions are allowed, provided they are reviewed and agreed before any publication.
04Central Approval
Final approval is the responsibility of AMN (AMN Design System Owner), not the company.
05Design & Code Alignment
Any impactful change must be updated in the design (Figma) and the SCSS/CSS files together.
06Shared Improvements
Any approved improvement is available to all companies and projects, not to a single project only.
07Version Control
Official updates are published in clear versions accompanied by Release Notes.
08No Unauthorized Changes
Modifying the shared standards outside the approved governance mechanism is prohibited.

Practical Examples

Practical examples showing how different cases move through the governance cycle
1Reuse

Use an existing Button

Use an existing button
The company needs a primary action button on one of the screens. It finds the approved Buttons component with its variants in the central library and uses it as is, without drawing a new button or writing a special style.
Case path in the workflow
03 Reuse Check→D1 · Yes→END · Reuse
Result
No request is needed; delivery continues using the approved component.
2EnhancementHypothetical scenario for illustration

Enhance an existing Table

Improve an existing table
The company needs extra behavior that the approved moi-table component does not cover (such as a new option for row actions). Instead of building a replacement table, it submits an improvement request on the same component explaining the need and why the existing one is not enough.
Case path in the workflow
03 Reuse Check→D1 · Enhance→04 Request→05 Review→06 Develop→07 QA→08 Publish
Result
The central component improves, and all projects benefit after the new release is approved.
3CodeHypothetical scenario for illustration

Extend an SCSS class

Extend an SCSS class
The company needs a neutral informational style for helper text under fields. It proposes a new modifier for the existing helper-row class (like the existing modifiers such as is-warning) built on the available Design Tokens instead of writing colors directly.
Case path in the workflow
D1 · Enhance→04 Request→05 Review→06 Develop→07 QA→08 Publish
Result
The class is merged into the central SCSS and documented, and becomes available to all companies.
4New VariantHypothetical scenario for illustration

Add a new Variant

Add a new variant
The company wants a new display state for the Tag component, which already has a Status property with several values. It requests a new Variant that follows the same property structure (Size / Variant) instead of drawing a standalone tag outside the library.
Case path in the workflow
D1 · Enhance→04 Request→05 Review→06 Develop→07 QA→08 Publish
Result
The variant is added to the central component in Figma and documented, and becomes available when the new release is published.
5Figma DesignHypothetical scenario for illustration

Update a component design in Figma

Update a component design in Figma
The company proposes improving the visual look of a specific state in the moi-uploader component. It submits the design in Figma including the States and the behavior description, with the matching SCSS/CSS if the code is affected.
Case path in the workflow
04 Request→05 Review→06 Develop→07 QA→08 Update Figma & Docs
Result
The main component in the central library is updated, and linked copies update after the library is published.
Note
The examples above are illustrative to simplify the idea; the component and class names mentioned are taken from the current system. Any real request goes through the same stages and is assessed by its actual need; none of these scenarios counts as pre-approval.

Glossary of Terms

Glossary of the terms used in the charts, with simplified definitions for design, development and management teams
English TermDefinitionMeaning in the AMN contextExample
Design System
An approved set of components, rules and assets that unify the look and behavior of products.
The central AMN system on which all projects and companies rely.
Figma + SCSS/CSS + documentation.
Governance
The framework of rules and roles that defines how decisions are made and changes approved.
The central review and approval mechanism for any change to the shared system.
An improvement request is not published before it is reviewed.
Workflow
An organized sequence of steps and decision points from start to end.
The path for delivering the system and proposing, approving and publishing improvements.
The main chart (A).
Handover
Transferring the official version of the system to a party that will use it, with its usage rules.
Delivering the approved resources to the company when it starts working within AMN.
Delivering Figma libraries, SCSS/CSS files and documentation.
Onboarding
Steps to introduce a new party to the system, its tools and rules.
Welcoming the new company and introducing it to the approved version and its responsibilities.

External Development Company
An external party that carries out projects within AMN.
The party that uses the system and submits improvement and addition requests.
A company developing a new module on the platform.
AMN Design System Owner
The party responsible for reviewing and approving system changes.
The team authorized to make the final decision at AMN.
Initial approval and final approval.
Central Library
The single official source of approved components, styles and code.
Gathers the approved Figma, SCSS/CSS and documentation versions.
The central Figma library.
Single Source of Truth
A principle requiring a single official source for information.
Any copy outside the central library is not considered approved.

A reusable interface element with a defined structure and behavior.

Variant
